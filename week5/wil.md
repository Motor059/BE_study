# 5주차 WIL: SOLID 원칙과 스프링 빈

---

## **객체 지향 프로그래밍 (OOP)**
- **객체 지향 프로그래밍**: 컴퓨터 프로그램을 여러 독립적인 부품들의 조합(객체들의 상호작용)으로 파악하는 패러다임으로, 묶음 단위로 잘게 쪼개서 조립하듯 전체 프로그램을 완성하여 유연하고 변경이 용이함
- **객체 지향의 4가지 특징**: 추상화, 캡슐화, 상속, 다형성
- **다형성**: 어떤 객체의 속성이나 기능이 상황에 따라 여러 가지 형태를 가질 수 있는 성질로 객체를 사용하는 클라이언트는 대상의 역할(인터페이스)만 알면 되며, 실제 구현의 내부 구조나 대상이 변경되어도 영향을 받지 않아 프로그램을 유연하게 만듦

## **SOLID 원칙**
- **SRP (단일 책임 원칙)**: 하나의 클래스는 단 한 개의 책임만 가져야 하며, 클래스를 변경하는 이유는 단 하나여야 함
- **OCP (개방-폐쇄 원칙)**: 클래스는 확장에 열려있어야 하며, 기존 코드의 수정에는 닫혀 있어야 함
- **LSP (리스코프 치환 원칙)**: 자식 클래스는 언제나 자신의 부모 클래스를 대체할 수 있어야 하며, 프로그램이 기대하는 방식으로 동일하게 작동해야 함
- **ISP (인터페이스 분리 원칙)**: 인터페이스를 클라이언트의 목적과 사용에 맞게끔 잘게 분리하여 제공해야 함
- **DIP (의존관계 역전 원칙)**: 구체화(구현 클래스)에 의존하는 것이 아니라, 추상화(인터페이스)에 의존해야 함

## **Spring Bean, DI, IoC**
- **IoC (제어의 역전)**: 객체의 생성 및 관리에 대한 제어권을 개발자가 아닌 스프링 프레임워크가 대신 가져가는 것
- **Spring Container & Bean**: 애플리케이션 전역에서 사용할 공용 객체를 스프링 빈(Bean)이라 하며, 스프링 컨테이너가 이 객체들을 저장하고 관리함
- **싱글톤 컨테이너**: 스프링 컨테이너는 매번 객체를 생성하는 대신, 객체를 딱 1개만 생성해서 필요할 때마다 재사용할 수 있게 하여 메모리를 효율적으로 사용함
- **DI (의존성 주입)**: IoC를 구현하는 방법으로, 내가 의존하는 객체를 직접 생성하지 않고 외부(스프링 컨테이너)에서 찾아 주입받는 것

## **의존성 주입 방법과 빈 충돌 해결**
- **생성자 주입**: 가장 권장되는 방식으로, 객체 생성 시점에 1번만 호출되는 것을 보장하고 롬복의 `@RequiredArgsConstructor`를 사용하여 final 필드에 대한 생성자를 자동으로 생성해 편리하게 주입할 수 있음
- **조회되는 빈이 2개 이상일 때의 해결법**:
    - **`@Primary`**: 여러 빈 중에서 우선순위를 정하여 가장 먼저 선택되도록 명시하는 방식
    - **`@Qualifier`**: 빈에 추가 이름표를 붙여, 여러 개의 빈 중 특정 이름표를 가진 빈을 사용하겠다고 명시적으로 지정하는 방식

## **SOLID 원칙 적용 리팩토링**
- 기존의 `Member`, `Product`, `Order` 도메인을 인터페이스(`Repository`, `Service`)와 구현체(`JpaRepository`, `ServiceImpl`)로 분리함
- 컨트롤러와 서비스 계층이 구체 클래스가 아닌 **인터페이스에 의존**하도록 변경하여 **DIP(의존관계 역전 원칙)**를 준수함
- `Memory` 구현체에서 `Jpa(DB)` 구현체로 변경될 때 기존 코드를 수정하지 않고 스프링 빈 주입(`@Primary`, `@Qualifier`)만 변경하도록 구성하여 **OCP(개방-폐쇄 원칙)**를 달성함
