# 2주차 WIL: 계층형 아키텍처와 컨트롤러, 서비스

---

## **스프링 계층형 아키텍처**
- **전체 구조**: 브라우저(클라이언트)의 요청은 컨트롤러, 서비스, 다오(레포지토리), 디비(DB)의 순서로 처리됨
- **컨트롤러 (Controller)**: 클라이언트의 HTTP 요청을 받고 적절한 응답을 반환하는 프레젠테이션 계층
- **서비스 (Service)**: 애플리케이션의 핵심 비즈니스 로직을 수행하고 트랜잭션을 관리하는 계층
- **레포지토리 (Repository / DAO)**: 데이터베이스와 직접 상호작용하여 데이터를 조회하거나 조작하는 계층
- **엔티티 (Entity)**: 데이터베이스 테이블과 직접 매핑되는 핵심 객체

## **데이터 전달 객체와 패키지 구조**
- **DTO (Data Transfer Object)**: 계층 간(Controller와 Service 간) 데이터 교환을 위해 사용하는 객체로, Entity를 직접 노출하지 않기 위해 사용됨 
- **패키지 구조**
    - **계층형 구조**: `controller`, `service`, `repository` 등 역할(계층)을 기준으로 패키지를 나누는 방식
    - **도메인형 구조**: `member`, `product`, `order` 등 관련된 도메인(업무)을 기준으로 패키지를 묶는 방식

## **웹 통신과 데이터 형식**
- **HTTP 데이터 구조**: 클라이언트와 서버 간 통신에 사용되며, 요청(메서드, URI, 헤더, 바디)과 응답(상태 코드, 헤더, 바디)으로 구성됨
- **JSON 구조**: 데이터를 키-값(Key-Value) 쌍으로 표현하는 경량 데이터 형식으로, API 통신에서 주로 사용됨
- **ResponseEntity**: 스프링에서 HTTP 상태 코드, 헤더, 바디를 세밀하게 제어하여 클라이언트에게 응답할 때 사용하는 객체로 `ok()`, `created()`, `build()` 등의 메서드를 제공함

## **스프링 핵심 개념과 동작 원리**
- **스프링과 스프링 부트**: 스프링 부트는 기존 스프링 프레임워크의 복잡한 설정을 자동화하여 애플리케이션을 빠르게 구축할 수 있게 해줌
- **스프링 애플리케이션 구조**: 내장 톰캣 서버를 통해 요청을 받고 스프링 컨테이너가 로직을 처리하는 전반적인 흐름
- **스프링 컨테이너와 빈**: 스프링 컨테이너는 애플리케이션 객체의 생명주기를 관리하는 공간이며, 빈은 스프링 컨테이너가 생성하고 관리하는 자바 객체
- **컴포넌트 스캔**: `@Controller`, `@Service`, `@Repository` 등의 어노테이션이 붙은 클래스를 자동으로 탐색하여 스프링 빈으로 등록하는 기능
- **의존성 주입**: 객체가 직접 의존성을 생성하지 않고 스프링 컨테이너가 외부에서 객체를 주입해 주는 방식으로 객체 간의 결합도를 낮추고 유연한 코드를 작성할 수 있게 해주는 핵심 원리
